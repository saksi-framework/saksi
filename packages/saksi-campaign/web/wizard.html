Generating ballots

These are the plaintext ballots, generated before any encryption — the population the encrypted election is built from, downloadable and checkable now.

Checking the data

Before anything is encrypted, the generated population is audited against itself: the ballot table is recounted from scratch and held against the published tally. A miscount, a truncated file, or a missing voter surfaces here rather than as a clean-looking result later.

Encrypting & recording

Each ballot is encrypted under the joint election key with a zero-knowledge proof that it is well-formed, then the election is closed so no further ballots can be accepted.

Threshold decryption ceremony

No single institution can read the result. Each holds one share of the key and contributes a partial decryption; the tally can only be opened once enough of them do.

Independent verification

The verifier re-derives the result from the published record alone and compares it against the ground truth seeded before the election. E is the total disagreement — it must be zero.

Bulletin board — declared result

Reset network for this tier

Runs tools/tier.sh (voters and positions from the form above): the Fabric network is torn down and brought back with an empty ledger, and the console picks up the new identity without a restart.

This destroys the ledger. Every election on the current network is gone from the chain. Run folders stay on disk, and each campaign's and run's export is the record: export before you reset.

Restart the peer mid-submission (T3)

Arms a fault on a generated on-chain run that is idle, is not a campaign repetition, has no attack plan and has not opened its ballot window. When that share of the ballots has been dispatched, peer0.org1.example.com is stopped for the chosen time while dispatch carries on; ballots sent meanwhile are recorded as drops.

The T3 flow: restart, resume, verify-only, verify.
  1. Restart the peer: arm the fault above, then continue that run through Check and Encrypt & record.
  2. Wait for the run to end. It ends failed with drops (“N of M ballots did not commit”), and the runs list shows it interrupted.
  3. Resume submits only the ballots the chain does not already hold, then closes the election. If the close fails, the error shows under the runs list: press Resume again when it is offered.
  4. Verify-only is required: it reconciles the chain's committed ballots against the run without submitting anything.
  5. Then the trustees, publish the tally and Verify: the ledger should match the local record with E = 0. The run is a security run; its throughput is not for RQ3.
With closed-loop dispatch (send rate 0) every ballot after the fault point fails within about a second, whatever down for says: to measure loss over the outage window, set a fixed send rate (Advanced) before generating the run.
If the console dies while the peer is down, the peer stays down. Recover it by hand: docker start peer0.org1.example.com, then check tools/up.sh status.
